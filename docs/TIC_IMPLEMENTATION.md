# Tidelight Intelligence Cloud implementation record

## Repository audit (15 October 2026)

Tidelight is a single Next.js 16 application on Vercel with Supabase Auth and Postgres. Existing market adapters live in `lib/bitget-market.ts`; SEC company facts, evidence collection, Agent Flow, strategy backtests, token pulse, and Nightwatch each have existing modules and routes. The current Agent Flow request has a 60 second Vercel duration and streams directly from the web request. Existing research data is owned by `user_id` and protected by RLS. The UI has Tidelight theme variables, branding assets, a workspace shell, and mobile styles.

Current capabilities are uneven. Bitget Reality spot rTokens and stock perpetuals are distinguished in the market adapter. The developer platform now has durable asynchronous company snapshot jobs, organization workspaces, and permission-scoped credentials. Commercial billing, OAuth authorization, an SDK release pipeline, and webhook dispatch are not active. No public developer credentials existed before these milestones. Existing live trading routes remain outside developer scopes.

## Architecture boundary

The first public API capability reuses `getBitgetMarketUniverse()` rather than a second provider implementation. `app/api/v1` owns the versioned external contract. `lib/tic` owns credential handling. `app/api/developers` owns cookie authenticated console operations. The developer UI is under `app/developers`. This grouping can be extracted into separate services and repositories later without moving core market logic into the UI.

The API checks a high entropy Bearer key through a service role only RPC. The RPC holds a key row lock while checking per-minute and monthly quotas and reserving a request record, so concurrent calls cannot bypass the limit. Project ownership is checked with the authenticated Supabase user before key issuance. Client roles have no direct grants or RLS policies on the new credential tables. A full secret is returned only on creation. The request log contains metadata, never headers or bodies.

The contract currently uses `tidelight.app/api/v1` so it can be deployed with the existing application. `api.tidelight.app`, `mcp.tidelight.app`, and `docs.tidelight.app` need routing and DNS review before they can be advertised. The landing page and docs inherit current Tidelight theme tokens and the developer routes bypass the trading workspace chrome.

## Milestone 2 — durable research snapshots (complete)

The implementation adds a service role only `tic_research_jobs` queue with project idempotency, key and project quotas, retry timestamps, bounded attempts, lease based claiming, cancellation, and expiring worker leases. `research:run` is a separate API scope. The Supabase `pg_cron` scheduler dispatches the Vercel worker over `pg_net`; its URL and dedicated bearer are held in Supabase Vault. The worker checks `TIC_RESEARCH_CRON_SECRET` and claims one job per invocation, runs the existing Bitget and headline discovery adapters, and stores a provenance labeled company snapshot. Market Reality spot instruments and USDT stock perpetuals remain separate instrument types. Headline snippets are labeled discovery references, and the result has explicit limitations. The public v1 API supports start, status/result, and cancellation. The console adds an owner scoped Research jobs page. Both in repository SDKs support job start/status/cancel and bounded polling. A project is limited to 10 job starts per rolling hour in addition to key call quotas.

Verification: production build, security and queue behavior passed local PostgreSQL tests; JavaScript (115), TypeScript SDK (3), and Python SDK (5) tests passed. The signed in production journey created a project and scoped key, read a live market instrument, started an NVDA snapshot, replayed its idempotency key, cancelled an AAPL job, and received the completed snapshot from the worker. The account-scoped console reported both statuses and seven authorized requests. The test key was revoked and immediately returned 401; the temporary user and its project, key, two jobs, and seven request records were deleted, with all related counts verified zero. The production Vercel worker accepted only authenticated requests. Supabase Cron dispatched through Vault-backed `pg_net` and received HTTP 200; the deployed worker returned a safe empty-queue response. Browser review covered the signed-out console and docs on mobile/desktop. Research-job view rendered at 390 px with no page overflow. A follow-up polish keeps the active navigation item in view when changing console sections on narrow screens.

## Milestone 3 — organization tenancy (implementation in progress)

The new migration backfills each existing developer into a private personal workspace and attaches their existing projects without changing API keys or idempotency history. New organizations support owner, admin, developer, and reader roles. Memberships, organization changes, audit history, projects, keys, usage, and jobs remain server mediated; anon/authenticated roles have no direct table or mutation-function grants. Existing project creator IDs become nullable attribution so project access is decided by organization membership. Adding or removing a member is limited to already registered Tidelight accounts because invitation email delivery is not configured. Removing a member or demoting them to reader revokes the API keys they issued in that organization. Job and usage views include all accessible organization projects. The console adds organization selection, member management, role updates/removal, and manager-only audit history.

Local PostgreSQL checks pass: fresh migrations backfilled an existing project; the legacy project-creation insert still receives a personal workspace; a second member issued a scoped key and started a shared project job; developers could not grant admin; demoting a member to reader revoked that member's key; removing a member revoked their key; revoked keys failed authorization; the final owner could not be removed; and `anon`/`authenticated` had no direct membership table or management function access. Shared request/job history survives user deletion with personal attribution cleared.

The first production owner/member smoke test found that `list_developer_organization_members` returned Auth's `varchar` email into a `text` result column, causing the member endpoint to return 503. PR #121 adds the cast and allows organization deletion cascades while preserving the live organization's last-owner check. It passed a PostgreSQL 17 regression check with Auth email set to `varchar(255)`, member listing, organization cascade cleanup, and account cleanup. Production verification then passed owner/member/reader access, real market and async research calls, idempotent retry, cancellation, key revocation, 403 permission denials, and outsider isolation. All temporary production users, workspaces, organizations, projects, keys, jobs, and usage records were deleted and zero counts verified. Production inspection at 390 px also led to PRs #122 and #123, which remove internal user IDs from the member list, allow long email wrapping, and disable last-owner controls.

## Milestone 4 — remote MCP server (complete for the current supported capability set)

The implementation uses the official TypeScript MCP SDK 1.32.1 with Streamable HTTP over Web Standard `Request`/`Response`, stateless mode, JSON responses, a 16 KB body limit, and DNS rebinding host/origin checks. `POST /api/mcp` exposes only tools available to the credential's scopes. Tool calls invoke the existing market/research REST handlers directly, so existing key authorization, request quotas, idempotency, and usage records remain in force. The current tool set is instrument search, tokenized equity lookup, company research start, job status, and job cancellation. API keys are the current bearer authentication mechanism; OAuth, MCP resources/prompts, and trading tools are not enabled.

Protocol tests use the official SDK client and server transports to validate initialization, tool discovery by scope, market provenance results, research job lifecycle calls, and denied tools. PR #124 deployed the endpoint. The production client test verified all five tools, a live Bitget Reality spot response with provenance, research start/cancel/status, market-only tool filtering, denied unauthorized calls, usage accounting, and immediate key revocation. It exposed a successful `error: null` status payload being misclassified; PR #125 fixed that behavior, with regression coverage, and deployed it to production. Production retest passed after deployment. The temporary account, organizations, projects, keys, jobs, and usage rows were removed; all corresponding database counts were confirmed zero. MCP documentation was visually checked in Chromium at 390 px and 1440 px with no horizontal overflow or page errors. Named third party MCP clients will not be advertised until individually tested. OAuth, resources, prompts, and trading tools remain disabled.

## External configuration still needed

Separate `api` and `mcp` hosts require DNS and Vercel domain configuration. Durable worker dispatch requires the dedicated `TIC_RESEARCH_CRON_SECRET` in Vercel Production plus `tic_research_worker_url` and `tic_research_worker_secret` in Supabase Vault before applying the scheduler migration. MCP OAuth requires issuer, client registration, consent, and token lifecycle infrastructure. SDK publishing requires package ownership and publishing credentials. Commercial billing needs pricing approval, payment provider eligibility and account configuration. Provider licensing must be confirmed before broad redistribution of market data.

Email invitation links require a verified transactional email sender and configured Supabase Auth templates. Until then, organization owners can add accounts that already exist in Tidelight.
